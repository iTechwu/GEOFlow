# 生产构建网络可靠性与回归记录

## 审查结论

生产构建的默认基础镜像存在三套不一致的来源：Composer vendor 阶段依赖 Docker Hub，Nginx 在 Dockerfile/Compose 中为 1.27、在环境模板和发布脚本中为 1.31.1，两份离线同步脚本也继续拉取官方短名。真实 `--pull` 构建进一步复现了 Docker Hub 元数据、BuildKit 远程 `ADD` 和 Debian 官方软件源的网络超时。

## 实施结果

- Composer vendor 阶段默认改用 `uhub.service.ucloud.cn/techwu/php:8.4-cli-bookworm`；固定 Composer 2.10.2 PHAR 仍单独下载并校验 SHA-256。
- Nginx 默认统一为企业仓库的 `uhub.service.ucloud.cn/techwu/nginx:1.31.1-alpine`。
- Dockerfile、Compose、环境模板、发布构建脚本和离线镜像同步脚本使用一致的基础镜像默认值。
- Composer PHAR 和 PECL Redis 归档改用容器内 `curl`，启用 HTTP/1.1、连接/总时限以及瞬时错误重试；校验失败仍会阻止镜像生成。
- Debian 软件源切换到阿里云镜像并启用 APT 重试；生产 Composer 默认使用阿里云 Packagist 镜像。
- 发布构建脚本补齐 `COMPOSER_PACKAGIST_MIRROR` 透传；显式空值仍可恢复官方 Packagist。
- 新增生产构建来源契约测试，拒绝旧的 `composer:2.10.2`、`nginx:1.27-alpine` 默认值，并锁定四类配置入口的一致性。

## 真实验证

- 企业 PHP CLI、PHP FPM、Node 24 和 Nginx 1.31.1 镜像元数据均可解析。
- 应用镜像以默认参数和 `--pull` 完整构建成功，Composer 2.10.2 与 PECL Redis 6.3.0 的 SHA-256 校验通过。
- Web 镜像以默认参数和 `--pull` 完整构建成功；`nginx -t` 与 `/nginx-health` 通过。
- 新应用镜像在 `common_network` 连接外部 PostgreSQL，`migrate:status --pending=1` 返回 `No pending migrations`。
- PHP 8.4.23 的 `gd`、`intl`、`mbstring`、OPcache、`pcntl`、`pdo_pgsql`、`pdo_sqlite`、`zip`、`redis` 扩展全部加载。
- 完整 PHPUnit：`1086 tests`、`8515 assertions`、`1 skipped`，无失败。

前端没有独立 `npm test` 脚本；两份生产镜像均已在资产阶段执行 `npm ci --no-audit --no-fund` 和 `npm run build`。第一次完整 PHPUnit 使用旧浏览器测试镜像时因缺少 GD/Zip 且挂载路径错误失败；切换到本轮构建并验收过的生产 PHP 运行时、使用 `/var/www/html` 正确路径后完整通过。
