## Standards

### S-P1：开发 Compose 未连接集中基础设施

根 `AGENTS.md` 第 5-7 行要求所有部署通过配置连接 `../docker-helm.dofe.ai` 的外部服务。生产与预构建 Compose 已整改，但开发链路仍不成立：

- `.env.example` 第 111、149 行仍使用集中编排中不存在的 `postgres.shared`、`redis.shared`。
- `docker-compose.yml` 第 141-142 行只声明本地 node_modules 卷，没有接入 external `common_network`。
- `docker/entrypoint.sh` 第 87-104 行继续以 `postgres.shared` 为默认值等待数据库。
- `make dev` 会从 `.env.example` 生成 `.env.local`，因此默认开发启动无法解析 `dofe-postgres`/`dofe-redis`。

建议让开发 Compose 同样接入参数化的 `common_network`，并统一默认服务名；若开发环境允许宿主机 DNS，则应提供单独且可运行的 profile，而不是保留不存在的默认别名。

### S-P2：新增提交规范后，后续提交仍使用英文类型前缀

`AGENTS.md` 第 11-12 行要求单功能提交且提交信息全部使用中文。规则在 `5ce8110` 引入后，`26aa530`、`a1387f7`、`be243b0`、`60d5de0` 仍分别使用 `feat:`、`fix:`、`docs:` 英文前缀。

建议明确规则是否允许 Conventional Commits 英文类型；若不允许，后续提交应使用纯中文主题，避免规范与实际流程持续冲突。

### S-P2：CI 的空白检查无法检查已提交内容

`.github/workflows/ci.yml` 第 52-53 行在干净 checkout 中执行 `git diff --check`，该命令只检查未提交差异。实际执行 `git diff --check d52f999...HEAD` 已发现 `AGENTS.md`、`CLAUDE.md` 的多余 EOF 空行和旧审查报告的行尾空格，但 CI 步骤在干净工作区会返回成功。

建议对 PR 使用 merge-base 到 `HEAD` 的差异运行 `git diff --check`，对 push 使用明确的前后 SHA。

### S-P2：当前工作区包含 0821 范围外的未提交改动

当前工作区还修改了后台欢迎页、Dashboard、footer、系统更新页、多语言文件及 27 个主题模板，并同时修改 agent 规范。这些不属于 models/MCP/CI 部署目标，不应与本次部署修复合并发布；应按功能拆分提交并单独验证页面与 SEO 行为。

### S-P3：MCP 与 REST 幂等执行流程重复

`McpIdempotencyService` 第 32-192 行重复了 `IdempotencyService` 的锁、预留、提交和释放流程。两套状态机后续容易产生租约、指纹版本或异常语义漂移。建议提取载荷无关的幂等执行内核，由 HTTP API 与 MCP 适配层分别提供请求哈希和响应转换。

## Spec

### R-P1：`notifications/initialized` 的 204 修复在运行时失败

`McpController::__invoke()` 返回类型是 `JsonResponse`，`notification()` 第 162 行也声明返回 `JsonResponse`；但第 165 行的 `response()->noContent()` 实际返回 `Illuminate\Http\Response`。该 `TypeError` 被控制器的通用异常处理转成 HTTP 200、JSON-RPC `-32000`，没有返回预期 204。

实际验证：

```text
Tests\Feature\McpEndpointTest
12 passed, 1 failed
Expected status 204, received 200
TypeError: McpController::notification(): Return value must be JsonResponse, Response returned
```

这发生在标准 MCP 初始化流程中，是当前 MCP 服务的发布阻断项。建议把控制器及通知方法返回类型调整为兼容 `Response`/`JsonResponse` 的基类或联合类型，并重新运行 MCP 及完整测试套件。

### R-P1：仓库内尚无全自动部署流水线

目标要求在 CI 机运行网页、MCP 和 Worker 并实现全自动化。当前 `geoflow-docker-deploy.sh` 已支持非交互首次安装，但 `.github/workflows/ci.yml` 第 8-53 行只在 GitHub 托管 runner 上安装依赖、检查边界、做语法检查和运行 PHPUnit；没有：

- 构建并发布应用镜像；
- 调用 CI 机上的非交互部署脚本或 Compose；
- 部署锁、环境审批、失败回滚；
- 部署后的网页、MCP、models、queue/scheduler/reverb 冒烟。

因此当前是“可被外部 CI 调用的部署脚本 + 验证 CI”，不是仓库内闭环的全自动部署。若部署由仓库外的 CI 配置触发，应把该配置和执行证据纳入验收；否则需新增面向 CI 机的部署 job/workflow。

### R-P2：MCP 声明的输入 Schema 没有在服务端执行

`McpController::tools()` 第 63-73 行声明类型、必填字段和 `additionalProperties: false`，但 `callTool()` 第 77-89 行直接强制类型转换，没有 Schema 或 Laravel Validator 校验。例如字符串 `"false"` 经 `(bool)` 转换为 `true`，会让 `geoflow.tasks.start` 意外执行 `enqueue_now=true`；字符串形式的任务 ID 和未声明字段也会被接受或忽略。

建议在调用业务 Service 前统一校验各工具 arguments，并对所有契约错误返回 `-32602`；补充错误类型、额外字段、边界长度和 `enqueue_now="false"` 的回归测试。

### R-P2：审计契约无法保证“每次写调用落库”

`03-MCP-契约.md` 第 48-52 行称写工具每次调用写入 `mcp_audit_logs`。但 `McpAuditLogger` 第 22-39 行捕获并静默丢弃所有 `Throwable`；表缺失、数据库故障或字段异常时，写操作仍返回成功，日志和指标中也没有审计失败信号。

建议明确采用 fail-closed 还是 fail-open。若保持 fail-open，至少写入结构化错误日志和指标并触发告警；文档应改为准确描述，而不是保证每次成功落库。

### R-P2：部署文档仍包含已失效的外部服务地址

生产模板已使用 `dofe-postgres`/`dofe-redis`，但以下文档仍使用旧地址：

- `docs/0821/04-CI部署运行手册.md` 第 17、22 行；
- `docs/deployment/DEPLOYMENT.md` 第 73、75 行；
- `docs/deployment/docker-prod-init-troubleshooting.md` 第 103-104、142-143 行。

旧 `06-当前实施审查报告.md` 也仍把已修复的生产网络和审计问题写成当前阻断。应在文档首页明确其历史状态，或归档到历史目录，避免运维人员按旧结论和旧主机名操作。

### R-P2：只读 Token 单独启用与部署脚本校验不一致

`03-MCP-契约.md` 第 7-10 行和 `AuthenticateMcpToken` 支持只配置 `GEOFLOW_MCP_READ_TOKEN`；但 `geoflow-docker-deploy.sh` 第 284 行在 MCP 开启时强制要求 `GEOFLOW_MCP_TOKEN` 非空。只读部署会被脚本拒绝。

建议按契约校验“写 Token 或只读 Token 至少一个非空”；如果生产策略强制写 Token，则反向修改契约和中间件说明。
