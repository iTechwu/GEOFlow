# 0821 当前实施复审报告

## 审查范围与结论

- 审查基线：`60d5de0`；增量提交：`b6527f8`（models `/internal/v1` HMAC 客户端）。
- 审查时间：2026-08-21。
- 结论：内部 HMAC 的签名算法与 models 守卫一致，但尚不能满足“所有大模型服务均通过 models 内部入口”的目标。存在两个 P1 问题，须在 CI 部署前修复。
- 本次增量未修改 Dockerfile 或 Compose，未重新引入 PostgreSQL、Redis、RabbitMQ，符合集中基础设施边界。

## Findings

### P1：长期运行的 Worker 会在五分钟后持续使用过期 HMAC 令牌

- 证据：`OpenAiRuntimeProvider::registerProvider()` 在注册时生成一次令牌，并用不含时间戳的固定 provider 名称缓存配置：[OpenAiRuntimeProvider.php](../../app/Support/GeoFlow/OpenAiRuntimeProvider.php#L217)。Laravel 的 `MultipleInstanceManager` 会按该名称缓存已解析实例，之后不会重读 config；Provider 构造时也保存 key 配置。
- 对端约束：models 的 `InternalAuthGuard` 将时间戳最大年龄限制为 300 秒：[internal-auth.guard.ts](../../../models.dofe.ai/apps/api/src/modules/internal-api/internal-auth.guard.ts#L219)。models 官方 SDK 则通过 `getAuthorization()` 在每个请求生成新签名：[internal-node.ts](../../../models.dofe.ai/packages/models-sdk/src/internal-node.ts#L46)。
- 影响：队列 Worker、常驻调度进程或 Octane 进程在首个请求五分钟后会收到 401，后续 AI 任务持续失败，直至进程重启。
- 建议：将签名生成放入每次出站请求的认证回调/HTTP 中间件；若框架限制，注册后显式清除对应 AI provider 实例并为每次调用重新解析。新增覆盖超过 300 秒、同一 Worker 连续两次调用的回归测试。

### P1：Embedding 与后台“测试连接”绕过内部 HMAC 路径

- 证据：知识库 Embedding 的元数据只识别 `hasUnifiedOverride()`，不识别 `hasInternalOverride()`：[KnowledgeChunkSyncService.php](../../app/Services/GeoFlow/KnowledgeChunkSyncService.php#L963)。随后直连 `/embeddings` 并以模型 API key 作为 Bearer Token：[KnowledgeChunkSyncService.php](../../app/Services/GeoFlow/KnowledgeChunkSyncService.php#L1155)。后台测试同样从 `IxicaiRuntimeCredentials` 获取公共/ixicai 凭据并直接 `withToken()`：[AiModelController.php](../../app/Http/Controllers/Admin/AiModelController.php#L185)、[IxicaiRuntimeCredentials.php](../../app/Services/Ixicai/IxicaiRuntimeCredentials.php#L27)。
- 影响：仅配置 `MODELS_INTERNAL_BASE_URL` 与 `INTERNAL_API_SECRET` 时，聊天类 Laravel AI 调用与 Embedding/后台校验分流，后两者仍走原模型地址或公共凭据，既不满足统一 models 内部接入，也无法在后台验证真实生产链路。
- 建议：为 chat、embedding 和连通性测试抽出同一套“按请求签名的内部 HTTP 客户端”，并先与 models 确认 `/internal/v1/embeddings` 的契约。当前 models 内部代理只公开 `chat/completions` 和 `responses`：[internal-proxy.controller.ts](../../../models.dofe.ai/apps/api/src/modules/internal-proxy/internal-proxy.controller.ts#L49)。

### P2：服务和租户上下文配置未实际发出，计费与审计会丢失归属

- 证据：新配置声明了 `MODELS_SERVICE_NAME`、`MODELS_TEAM_ID`：[geoflow.php](../../config/geoflow.php#L108)，但注册链路明确生成两段令牌且传入 `null` 服务名：[OpenAiRuntimeProvider.php](../../app/Support/GeoFlow/OpenAiRuntimeProvider.php#L219)，也没有设置 `x-service-name`、`x-team-id` 或 `x-api-key`。
- 影响：models 守卫会把调用方记录为 `unknown`；内部代理只有在收到 `x-team-id` 时才记录租户定价和销售额：[proxy-core.service.ts](../../../models.dofe.ai/apps/api/libs/domain/proxy-core/proxy-core.service.ts#L2121)。当前流量将没有 GEOFlow 服务归属，也不会产生 team 维度计费记录。
- 建议：使用三段签名令牌并随请求发送 `x-service-name`、`x-team-id`；若 Laravel AI SDK 无法附加这些头部，改用可注入 headers 的网关客户端。删除未被消费的配置/`headers()` 抽象，或为其补上端到端覆盖。

### P2：MCP JSON-RPC 通知回归失败，实施记录与真实行为不符

- 证据：`notification()` 声明返回 `JsonResponse`，却在无 id 时返回 `response()->noContent()` 的普通 `Response`：[McpController.php](../../app/Http/Controllers/McpController.php#L162)。
- 影响：PHP 抛出 `TypeError`，框架最终返回 200 而非 JSON-RPC 通知要求的 204；`McpEndpointTest` 的 13 项中 1 项失败。`05-实施与验证记录.md` 仍声称该行为已整改：[05-实施与验证记录.md](05-实施与验证记录.md#L53)。
- 建议：将该私有方法及调用方的返回类型放宽为 `Response`/`ResponseFactory` 可返回的共同类型，或让通知分支在控制器中直接返回 204；保留现有回归测试，并纠正实施记录。

### P2：0821 文档仍将本次已实现的 HMAC 记为“后续工作”

- 证据：[02-models-接入.md](02-models-接入.md#L18) 和 [05-实施与验证记录.md](05-实施与验证记录.md#L58) 都写明本次未实现内部签名客户端，但 `b6527f8` 已新增实现。
- 影响：部署人员会依据过期文档配置公共 `/v1`，且无法了解内部入口的已知限制。
- 建议：修复上述文档，并在部署手册中增加内部入口开关、所需 secret、team ID、支持端点、令牌刷新和回退策略。

### P2：提交与工作区未遵守提交纪律

- 证据：`b6527f8` 的提交标题以英文 `feat:` 开头，违反根目录 `AGENTS.md`“提交信息全部使用中文”的要求。当前工作区还同时累积 agent 规范和后台/主题改动，尚未拆分提交。
- 影响：历史可读性与变更回滚边界变差，后续审查无法稳定定位功能变更。
- 建议：后续功能采用纯中文提交标题；将现有未提交的不同主题拆成独立提交。不要重写已共享提交历史，除非团队明确批准。
